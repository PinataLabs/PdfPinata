# Spec — Generating the DOM's `Serialize` methods

§8 of [`compile-time-dom-value-model.md`](compile-time-dom-value-model.md) deferred this and said
why:

> It is not in this spec because the irregular cases are the majority of the work, not the edge […]
> Any generator would need an escape hatch broad enough that it stops being obviously safer than the
> hand-written code.

That was a judgement made by reading a handful of methods. This spec starts by measuring it, because
the measurement changes the answer: it is not that the irregular cases are a majority, it is that
**the regular ones are a fifth**, and the irregular tail contains three methods so bespoke that no
generator should ever touch them.

The conclusion, up front, so the rest can be read as evidence for it: **do not generate `Serialize`.
Generate the flat run of attribute writes that sits inside it, let each type keep ownership of its
own method, and add the diagnostic that catches the bug §8 actually named** — a `[DV]` member added
to a class and forgotten in `Serialize`.

---

## 1. The measurement

Every `Serialize` method in `PinataLayout.DocumentObjectModel` was classified against a grammar of
what the value model already knows how to emit:

* `BeginContent` / `EndContent` / `BeginAttributes` / `EndAttributes` / `base.Serialize`
* `if (member != null)` — or `if (!member.IsNull)`, or `if (!IsNull("Name"))` — guarding a
  `WriteSimpleAttribute("Name", Property)` or a nested `child.Serialize(serializer)`
* a fixed prologue: `WriteComment(comment ?? "")`, a `WriteLine("\keyword")`, a
  `child.Serialize(serializer, "Name", null)`
* the reference-object comparison family: `if (member != null && (refX == null || Member != refX.Member))`

Anything else counts as *odd* — a statement a generator would have to be told about by hand.

| odd statements | methods | cumulative |
|---|---|---|
| 0 | 15 | 15 (20%) |
| 1 | 13 | 28 (37%) |
| 2 | 9 | 37 (50%) |
| 3 | 12 | 49 (66%) |
| 4 | 8 | 57 (77%) |
| 5 | 8 | 65 (87%) |
| 7–10 | 6 | 71 (95%) |
| 22, 32, 38 | 3 | 74 (100%) |

74 methods: 67 `internal override void Serialize(Serializer)` plus seven overloads that take a name
or a reference object.

Two things fall out of that table, and they point in opposite directions.

**Half the methods are within two statements of being pure value-model output.** That is a much
better position than §8 implied, and it is what makes partial generation worth doing at all.

**The tail is not a tail.** Three methods are essentially entirely bespoke:

| method | odd / total | what it does instead |
|---|---|---|
| `Font.Serialize(Serializer, Font)` (`Font.cs:323`) | 38 / 65 | Builds `\bold\italic`-style shortcuts, inspects `CheckWhatIsNotNull()`, and branches on whether the parent is a `FormattedText` |
| `Style.Serialize` (`Style.cs:336`) | 32 / 36 | Five-way branch on built-in vs user-defined, resolving a reference style through `Styles.BuildInStyles` and `Document.Styles` |
| `Character.Serialize` (`Character.cs:134`) | 22 / 22 | Emits `\tab`, `\linebreak`, `\space(...)`, `\symbol(...)` or `\chr(0x...)` by testing the top nibble of a raw value |

None of these writes a single `WriteSimpleAttribute`. A generator that covered them would be a
second implementation of the DDL writer, not a table lookup.

## 2. What the regular part looks like

`LineFormat.Serialize` (`LineFormat.cs:125`) is one of the 15, and is the whole of the case for
generating anything:

```csharp
internal override void Serialize(Serializer serializer)
{
    int pos = serializer.BeginContent("LineFormat");
    if (this.visible != null)
        serializer.WriteSimpleAttribute("Visible", this.Visible);
    if (this.style != null)
        serializer.WriteSimpleAttribute("Style", this.Style);
    if (this.dashStyle != null)
        serializer.WriteSimpleAttribute("DashStyle", this.DashStyle);
    if (!this.width.IsNull)
        serializer.WriteSimpleAttribute("Width", this.Width);
    if (!this.color.IsNull)
        serializer.WriteSimpleAttribute("Color", this.Color);
    serializer.EndContent();
}
```

Every line of that is already declared by `[DV]`. The guard differs only by `ValueKind` — `!= null`
for `Leaf`, `!X.IsNull` for `NullableValue` — which is exactly the distinction the value model was
built to carry.

`Chart.Serialize` (`Chart.cs:545`, 1 odd of 42) is the other end of what is still worth generating:
a `\chart(Type)` line the generator cannot know, then a long flat run it entirely can, then a
hand-imposed ordering of eleven child objects into a content block. The flat run is generable; the
ordering is a decision, and decisions belong in the source file.

## 3. The design

### 3.1 Generate a method, not the method

For each `[DV]`-carrying type, the generator emits into the existing partial class:

```csharp
// <auto-generated/>
partial class LineFormat
{
    /// <summary>Writes every [DV] member that is set, in declaration order.</summary>
    internal void SerializeValues(PinataLayout.DocumentObjectModel.Serializer serializer)
    {
        if (visible is not null)
            serializer.WriteSimpleAttribute("Visible", Visible);
        // ... one block per member, guard chosen by ValueKind
    }
}
```

and the hand-written method shrinks to:

```csharp
internal override void Serialize(Serializer serializer)
{
    int pos = serializer.BeginContent("LineFormat");
    SerializeValues(serializer);
    serializer.EndContent();
}
```

This is the escape hatch §8 said any design would need, and it is as narrow as it can be: the
generator owns a run of attribute writes, the type owns everything around it. `Chart` calls
`SerializeValues` in the middle of its own method and keeps its ordering. `Character` never calls it
at all and loses nothing.

The generator already emits `partial class X { private static readonly Meta GeneratedMeta = …; }`
(`Emitter.cs:28-50`), so this is an additional member in a file that already exists, not new
plumbing.

### 3.2 The reference-object overload

Four methods compare each member against a corresponding member of a reference object before
writing it — `Border`, `Borders`, `ParagraphFormat` and `Font`. Three of the four are otherwise
regular (2–4 odd statements out of 12, 32 and 40), and between them they are the largest flat runs
in the DOM. They earn a second generated shape:

```csharp
internal void SerializeValues(Serializer serializer, ParagraphFormat refFormat)
{
    if (alignment is not null && (refFormat is null || alignment != refFormat.alignment))
        serializer.WriteSimpleAttribute("Alignment", Alignment);
    // ...
}
```

Note that the comparison is against the *field*, not the property, in `ParagraphFormat`
(`ParagraphFormat.cs:431` onwards) and against the property in `Border` (`Border.cs:172`). Those are
not equivalent for a `NullableValue` member, and the generator must reproduce whichever the type
does today rather than picking one — see §4.

`Borders` adds a third guard clause (`refBorders.visible == null ||`) that the other three do not.
That asymmetry is either deliberate or a bug; **this spec does not resolve it**, it reproduces it,
and it should be raised separately.

`Font` takes the overload and is otherwise 38-odd; it opts out of generation entirely and keeps its
hand-written body.

### 3.3 Opt-in, not opt-out

The generator emits `SerializeValues` for every type. Whether a type *calls* it is the author's
choice, made in the hand-written `Serialize`. An unused generated method costs a few bytes of IL and
nothing else, and this way no type is ever silently switched over.

That also means the migration is incremental at the granularity of one type, and every step is a
diff a reviewer can check by eye against the method it replaces.

### 3.4 MDG007 — the diagnostic that is the actual point

§8's stated motivation was: *"a member added to a class but forgotten in `Serialize` is a bug the
compiler could catch instead of a round-trip test."* That does not need generation at all.

Add a diagnostic: for a type that declares `[DV]` members and overrides `Serialize`, warn when a
member's `ValueName` appears in no string literal in the type's `Serialize` methods and the type does
not call `SerializeValues`.

It is a deliberately crude test — a string-literal scan, not dataflow — and it will be wrong for
`Character`, `Text`, the eight `Field` types and the other keyword-writers that never name their
members. Those suppress it once, in source, with a reason. That is the right trade: a one-line
suppression on a dozen genuinely bespoke types, in exchange for the check firing on all the others.

**MDG007 is worth shipping on its own, before any generation.** It is the cheapest item in this
document and the only one that finds bugs rather than deleting code.

## 4. Byte-for-byte is the gate

This is the constraint that makes the work hard, and it is worth stating before any code is written.

**The generated order is not the hand-written order.** F6 of
[`dom-value-model-findings.md`](dom-value-model-findings.md) records that the generated model orders
members base-class first, then source position. The `Serialize` methods order their writes by hand,
and the two agree only by coincidence. Where they disagree, the emitted DDL changes — attributes come
out in a different order — and every round-trip test that compares strings will notice.

So the acceptance criterion is not "the tests pass". It is:

* A corpus of documents — the ones `DdlRoundTripTests`, `FormattedTextFontRoundTripTests` and
  `BorderClearedTests` already build, plus `MigradocTurkishTest`'s and the chart samples — is
  serialized before and after each type is switched over, and the output is compared **byte for
  byte**.
* Any difference is either reverted, or is a deliberate reordering with a note in the release notes.
  Silent reordering is the failure mode this whole spec exists to avoid, because DDL is a file
  format users diff.

This is the same shape as the value model's parity harness, which ran 339 assertions comparing the
generated model against the reflection one. That harness is the precedent and the reason to believe
this is tractable: it caught two real defects (F1 and F2) precisely because it demanded equality
rather than plausibility.

A second, cheaper gate for the flat run: `Verify` is already used in this repo, so a snapshot test
over `Emitter`'s output would catch a formatting or escaping regression in the generated
`SerializeValues` directly, rather than through a document. That is the same gap the findings
document records for the value model's emitter, and doing both at once is cheaper than doing either
twice.

## 5. Sequencing

| # | step | why here |
|---|---|---|
| 1 | **MDG007** and its suppressions | Finds bugs, deletes nothing, independent of everything below |
| 2 | The byte-comparison harness over the existing corpus | Nothing after this is safe without it |
| 3 | `Emitter` emits `SerializeValues`; **no type calls it** | Proves the generated code compiles and binds across all 67 types with zero behaviour change |
| 4 | Switch over the 15 zero-odd methods | The diff is a deletion; the harness proves it byte-identical |
| 5 | Switch over the ≤2-odd methods that read cleanly | 22 more; stop at the first one that needs the generator to learn a new shape |
| 6 | The reference-object overload, for `Border`, `Borders`, `ParagraphFormat` | §3.2, including reproducing `Borders`' extra guard |

Steps 1 and 2 are worth doing whether or not 3–6 ever happen.

**Never:** the nine methods at seven or more odd statements — `Font`, `Style`, `Character`, `Styles`,
`Hyperlink`, `HeadersFooters`, `HeaderFooter`, `DocumentElements` and `FormattedText`. They are
hand-written because the DDL they emit is hand-shaped, and the generator has nothing to offer them.

**Probably not, despite being close:** the eight `Field` types, `Text`, `TabStops`, `Point` and the
collection wrappers (`Cells`, `Sections`, `SeriesCollection`, `XValues`), which sit at three to five
odd statements only because they build a keyword string by concatenation rather than writing
attributes. They are near-regular by statement count and not at all regular in what they do; step 5
should stop at them rather than teach the generator string-building.

## 6. Why not go further

Three positions were considered.

**Generate the whole method.** Rejected. It requires modelling `\chr(0x…)`, the `\bold` shortcut,
`Style`'s five-way reference resolution and the `Hyperlink` obligatory-property throw. Each would
enter the generator as a special case keyed by type name, which is the escape hatch §8 warned about:
at that point the generator is a less readable copy of the code it replaced.

**Generate nothing, keep MDG007 only.** Defensible, and strictly better than the status quo. What it
forgoes is real: the 37 methods at two or fewer odd statements contain **494 statements the model
could emit**, most of them `if`/`WriteSimpleAttribute` pairs, and leaving them hand-written leaves
their ordering free to drift from the model that declares them. Recommended as the fallback if step 4
turns up more byte differences than expected.

**A declarative attribute — `[DV(SerializeAs = …)]`.** Rejected as premature. It moves the
irregularity from C# into attribute arguments without reducing it, and the three worst methods would
need an expression language to describe. If the flat run is generated and the bespoke methods are
left alone, there is nothing left for it to declare.

## 7. MDG007, shipped

Step 1 landed: `PinataLayout.DocumentObjectModel.Generators/Diagnostics.cs` has
`MemberMissingFromSerialize`, and `Parser.cs` scans every method literally named `Serialize` for a
mention of each of the type's own `[DV]` members — a string literal (`WriteSimpleAttribute("Style",
…)`) or a plain identifier (`Columns.Serialize(serializer)`, `WriteComment(comment)`), matched
case-insensitively since a member is typically camelCase and its DDL-facing name is PascalCase. §3.4
predicted this would misfire on `Character`, `Text`, the eight `Field` types and the other
keyword-writers; in the event, none of them did — the identifier half of the scan (not literals
alone) already covers every one of those, because a keyword-writer still refers to its own field
somewhere, just never inside a `WriteSimpleAttribute` call. Nothing in that predicted list needed a
suppression.

Only two members did: `Row.index` and `Column.index`, which are recomputed from the row's or
column's own position in its collection rather than stored, so there is nothing for `Serialize` to
write. Both carry `[SuppressSerializeCheck("…")]` on the type.

Everything else the diagnostic found is real: `HeaderFooter.style`, `Hyperlink.font` and
`Table.KeepTogether` are each read by the renderer (`ParagraphRenderer`, `TableRenderer`) but never
written by their type's `Serialize` — set one, save the document, reload it, and the setting is
gone. These are left as live warnings rather than fixed here: touching `Serialize` is exactly what
§4's byte-comparison harness exists to make safe, and step 2 landed alongside MDG007 -
`DdlByteComparisonHarnessTests` and `Golden.cs` in `PinataLayout.DocumentObjectModel.Tests` pin six
corpus documents against the DDL a correct `Serialize` produces today. Fixing the three warnings
above is now safe to attempt; it is still not done here.
