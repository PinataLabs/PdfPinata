# Spec — streams whose /Length is wrong, issue #29

[empira/PDFsharp#29](https://github.com/empira/PDFsharp/issues/29) reports
`PdfReaderException: "Unexpected token 'e' in PDF stream. The file may be corrupted."` on a PDF
generated by Microsoft Learn. The answer on the issue names the cause: *"The specified lengths of
more than 1600 streams in the PDF file are too short."*

This fork already recovers from a stream whose `/Length` is missing
(`docs/specs` has no note on it; see `StreamWithoutLengthTests`, issue ststeiger#469) and from one
whose `/Length` lives in an object stream (`IndirectStreamLengthTests`, issue ststeiger#456). A
`/Length` that is merely **wrong** was a different matter, and it was wrong in three ways.

| item | what | status |
|---|---|---|
| 1 | A stream one byte short is silently truncated | done |
| 2 | Recovery only works when a line feed precedes `endstream` | done |
| 3 | A `/Length` past the end of the file trips an assertion | done |

---

## Where the 'e' comes from

`Parser.ReadSymbol` had a special case for the keyword that ends a stream:

```csharp
if (symbol == Symbol.EndStream)
{
    Skip:
    char ch = _lexer.MoveToNonWhiteSpace();
    if (ch != 'e' && ch != Chars.EOF)
    {
        _lexer.ScanNextChar(false);
        goto Skip;
    }
}
```

After reading the declared number of bytes it walked forward to the next `e` and scanned a token
there. That is the whole of the reported error and the whole of item 1:

- the tail the length left behind contains an `e` that starts something else — `re S` in a content
  stream — so the token read is `e`, and the reader throws **"Unexpected token 'e'"**;
- the tail contains no `e` at all, so the walk lands on the real `endstream`, the reader is
  satisfied, and **the tail is dropped from the stream without a word**. `/Length` one short loses
  the last byte of every such stream.

The first at least says something. The second is worse: a document reads, and the content stream,
the image or the embedded font is one byte short of what the file holds.

The skip is gone. What follows the declared data now has to be white space and then `endstream`,
which is what §7.3.8.1 says is there. Anything else means the length did not describe the stream,
whatever it said, and the reader falls back on the recovery it already had — scanning for the
keyword that ends the stream, and recording the length it found so that the dictionary describes
what it now holds.

The recovery was already reached this way; it was only reached when the tail happened to hold an
`e`. This makes it reached whenever the length is wrong.

## Item 2 — the keyword is what ends a stream, not the line feed before it

`TryReadStreamUpToEndOfStream` scanned for `"\nendstream"`. A producer careless enough to get the
length wrong is not one to be relied on to put the end-of-line there either, and three of the four
shapes — `\r`, a blank, and nothing at all before the keyword — left the recovery finding nothing
and the reader rethrowing.

It now scans for `endstream` and drops the end-of-line before it from the data, since that
end-of-line belongs to the file rather than to the stream. A blank is kept: the specification puts
an EOL there, not white space in general, so a blank is as likely to be the last byte of the data.

## Item 3 — a length longer than the file

`Lexer.ReadStream` read the declared number of bytes into a buffer of that size and asserted that
it got them:

```csharp
int read = _pdfSteam.Read(bytes, 0, length);
Debug.Assert(read == length);
```

A `/Length` of 500 in a file with 100 bytes left is a failed assertion in a debug build — under
xUnit, `DebugAssertException` — and 400 zero bytes appended to the stream in a release one. The
single `Read` was also assuming a stream fills the buffer it is given, which is not something a
`Stream` promises.

The parser now treats a length reaching past the end of the file as no length at all, and takes the
same recovery it takes for a missing one. `ReadStream` reads through `StreamHelper.ReadUpTo` and
hands back what it got.

That leaves the parser to notice when what it got is short. The position it notes as the start of
the stream is where the lexer stands, which is the end-of-line behind the `stream` keyword and not
the first byte of the data — so a length reaching to exactly the last byte of the file fits the
file by a byte it cannot use, and comes back one byte short. Reading on from there finds the end of
the file, and `ReadSymbol` lets an unexpected end of file pass, so the truncated stream would be
accepted without the keyword that ends one and without a word — item 1 again, by another road. A
short read is therefore a length that did not describe the stream, and takes the recovery.

---

## What this changes for documents that read today

A document whose `/Length` is right reads exactly as before: the check that follows the data is
the same token read that was there before, minus the walk to the next `e`.

A document whose `/Length` is right but which holds something other than white space between the
data and `endstream` now goes through the recovery, and that junk ends up inside the stream where
before it was skipped. Such a document is rarer than one with a wrong length — the issue's single
file has more than 1600 of the latter — and the recovery hands back what the file holds rather
than dropping bytes from it, which is the trade this makes deliberately.

## Verification

`PdfPinata.Test/IO/WrongStreamLengthTests.cs`, 17 tests: lengths short by 1, 5 and everything,
long by 5 and by more than the stream, a compressed stream short by 5, all four ways a stream can
end without a line feed, a wrong length given indirectly, a length longer than the file, one
reaching to exactly the end of it, the recovered length being recorded, and a stream that never
ends still being reported as unreadable. On `master`, 10 of them fail. Two of those are the silent truncation: a content stream one byte
short reads one byte short, and a compressed stream one byte short fails to inflate at all
("Unexpected EOF" out of SharpZipLib), which is what that dropped byte costs a document that is
not plain text.

The 94 MB, 3288-page document the issue links to was read alongside, outside the suite: it opens in
about 10 seconds, saves, and reads back with all 3288 pages, before and after the change.

Whole suite green on net8.0 and net10.0, 1056 passed on each, one pre-existing skip
(`CanCreatePdfOver2gb`). Release build with 0 warnings.

## Not in scope

- **A `/Length` one byte too long.** The extra byte is the end-of-line before `endstream`, and the
  keyword still follows where the reader looks for it, so nothing distinguishes that byte from
  data the stream really ends with. It is kept.
- **Rebuilding a document whose cross-reference table is also wrong.** That is what
  `PdfReadAccuracy.Moderate` is for, and it is unchanged here.
